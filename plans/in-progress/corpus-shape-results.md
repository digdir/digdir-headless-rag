# Corpus shape — digdir/public-docs (website pipeline)

Date: 2026-05-26
Branch: establish-baseline
Typesense: `typesense-test.digdir.cloud:443` (resolved via platform
config from the cloned DB `dh_bb_dev_establish_baseline_v1`)

Preparatory characterization for the multi-variable sweep
(see `plans/proposed/multi-variable-sweep-experiment-plan.md`). This
document captures *what is in the data*, not retrieval quality. The
actual performance baseline is a separate step.

## How this was produced

Built interactively via ~12 small probes through the new
filesystem-style debug tools landed in commit `8e44054` + `963ea1e`:

```
bb ts-search digdir public-docs <role> "<q>" [--facet-by …] [--filter-by …]
bb ts-get    digdir public-docs <role> --ids <id1,id2,...>
```

Tools run via `mise exec -- bb <task>` so worktree-local
`RAG_API_BASE_URL` (8181) is respected instead of the parent
config's 8081. `bb ts-retrieve` was intentionally NOT used for this
characterization — it's gated off so the multi-strategy retrieval
skill's contribution can be isolated in the actual sweep.

## Schemas (live, minimum common shape)

- **docs**: `doc_num, title, url, lastmod, type, total_chunks`
  (no `metadata`, no `orgs_long`/`orgs_short`/`content_length` on the
  website pipeline)
- **chunks**: `chunk_id, doc_num, chunk_index, content_markdown,
  metadata, content_length, url` — note `title` is NOT here; it
  lives on docs and is reached via the `$docs(url,title)` join
- **phrases**: `chunk_id, doc_num, search_phrase, phrase_vec`
- **enrichment / verified-phrases**: `chunk_id, doc_num, phrase,
  phrase_vec, model, prompt_hash, generated_at`
- **enrichment / fact-assertions**: `chunk_id, doc_num, subject,
  predicate, object, triple_text, triple_vec, model, prompt_hash`

## Phrase coverage

Skewed:

- Average: 7,456 ÷ 5,919 = **1.26 phrases per chunk**
- Top 10 chunks carry 16–26 phrases each (≈190 phrases / 0.17% of
  chunks)
- Most chunks have 0–2 phrases

The skew matters: the phrase-similarity retrieval strategy will
contribute much more on the long-tail chunks than on the head, so
sweep cases that target phrase-poor chunks will see different
attribution than cases on phrase-rich chunks.

## Implications for the upcoming sweep

1. **Enrichment dimensions are narrow.** Sweep cases comparing
   "verified-phrases ON vs OFF" can only show signal on the 10
   enriched chunks; "fact-assertions ON vs OFF" on the 4. If the
   benchmark question set doesn't target those chunks specifically,
   the enrichment dimension reads as no-signal or noise.
2. **Hypothetical-questions is empty.** Any sweep dimension involving
   that enrichment is currently a null cell. Either generate the
   enrichment first or drop the dimension from Round 1.
3. **The 82 zero-chunk docs are dead weight.** Worth checking
   whether they were intentional (e.g. failed scrape) — they don't
   contribute to retrieval but inflate the docs collection.
4. **Phrase skew suggests strategy-weight sweeps should split by
   chunk-phrase-density.** A balanced strategy mix vs a phrase-heavy
   one will land very differently on a phrase-poor chunk than on
   the heads of the phrase distribution.

## Two UX rough edges noted

These don't block the sweep but are worth fixing alongside future
exploration:

1. `bb ts-search docs --query-by url "/nb/"` does NOT give a
   per-language URL split — Typesense tokenizes slashes, so `/nb/`
   matches by token presence (only 10 hits). Pre-aggregating per-
   language counts would need either a dedicated `language` field on
   docs or a substring filter (not supported by Typesense `filter_by`).
2. zsh interprets backticks in `--filter-by 'chunk_id:=`abc`'` as
   command substitution before bb sees them. Single-quoting the
   whole argument *and* avoiding backticks where possible
   (alphanumeric ids don't need them anyway) is the practical fix.
   Consider documenting this in `bb ts-search` `--help` if more
   contributors hit it.
