Speaker notes Frame: this isn't just "a RAG pipeline" — it's a multi-tenant platform we could experiment ON. Two intertwined stories: (1) the architecture that made experimentation cheap, and (2) the research journey to make retrieval actually good — where most of the hard-won lessons live.

One resolution, one context

Auth resolves the key to a permission scope; context resolution walks the config tree once to produce a fully-resolved execution context (tenant + dataset + agent policy + merged config). Handlers never redo config I/O.

Pure core, impure edge

execution.scope is pure normalization + config reads — reusable from pipelines, CLI, background jobs. Only api.context knows about HTTP. API-key scope enforcement is centralized, not re-checked per handler.

Speaker notes The discipline here: assemble context once, pass it through. Traces are preserved all the way down so the Playground can show why each config value won.

Architectural pillar 1Everything is a config tree

A Datahike-backed inheritance tree resolves every runtime setting per request. Ask for a path; the system walks the tenant's ancestors and returns the first hit.

  • Three roots partition definitions: platform (infra/secrets), runtime (agent/skill behavior), dataset (source + chunking).
  • Deterministic single-winner resolution — single-parent trees, upward walk, first ancestor wins.
  • Stateless multi-tenancy — tenant is never in env; every request names its own.
Why this was the platform bet

Prompts, retrieval knobs, top-K, rerank flags, model choice — all live as config. A new experiment is a config write, not a redeploy. This is what made hundreds of A/B sweeps affordable.

ABACuser attributes × definition attributes, per-path-prefix rules cryptoAES-256-GCM, PBKDF2-SHA256 (100k), secrets ciphertext-only auditevery mutation: actor, before/after, redacted trace*-with-trace returns the winning ancestor — explainability
Speaker notes Rough edges to be honest about: several trace / non-trace resolver variants are near-duplicates; a couple of ops namespaces are deprecated alias shims. Prototype tax.

Architectural pillar 2Skills wired as a graph

A skill is a typed unit of work — schema-validated I/O. A graph wires skills into a DAG. One runner executes them topologically.

  • Graphs are data — no macros, no runtime compilation. Serializable, inspectable, swappable.
  • Typed I/O at boundaries — wiring mistakes caught on load (Kahn's algorithm; cycle + forward-ref checks), not mid-run.
  • Skills are thin — the hard work is in rag.* / llm.*; skills just adapt I/O.
One runner, two sources

The same engine runs compile-time templates and graphs the agent synthesizes at runtime — so observability and error handling are shared.

Design objectives (as built)

  • Deterministic retrieval — fixed config + index ⇒ reproducible search→merge→rerank. Only synthesis is non-deterministic ⇒ replay, diff, debug.
  • Explicit attribution — every hit carries its strategy tag through merge.
  • Enforced citation — synthesis always emits [N]; post-parse flags unsourced claims.
Auto-filter

Query text is scanned for org names + years against a cached Typesense facet list; matched filters are injected automatically — so "Digdir 2022" narrows without the caller building a filter spec.

Swappable rerank: the skill wraps the core so the reranker can change without touching retrieval or synthesis. That seam mattered — see next section.

Speaker notes Foreshadow: "the reranker can change without touching retrieval" is exactly the seam that let us fix the biggest quality bug. Hold that thought.

Architectural pillar 4The agentic loop — skills as tools

A ReAct loop that calls retrieval / read / rerank / synthesis as tools, with structured evidence gates and hard budgets.

  • Definition vs execution — an agent is a durable config row (allowed graphs, dataset scopes, guardrails) and a code-driven loop. Grant scopes / change instructions as data; change behavior as code.
  • Tools bridge to skills — a new retrieval heuristic reaches the agent for free.
Two guardrails against the LLM-loop footgun
hard budgetsevery tool call decrements; exhaustion forces finalize read-signalsper-claim: support-found / gap / conflicting sufficiencycontinue · read more · clarify · finalize
Structured evidence, not "are you done?"

search returns metadata only (LLM spends no context on bodies it hasn't chosen to read); read_chunks materializes on demand. Evidence evaluation is separate LLM calls with their own schemas.

Speaker notes Deliberate choice: the loop calls OpenAI/Anthropic directly, not through the litellm wrapper, to preserve multi-turn tool_calls context. Cost: provider handling duplicated here. Worth it.

Architectural pillar 5The Playground — observability as a first-class surface

Same pipeline as production, plus deep observability: live event streams, per-stage diagnostics, evidence tables with rerank scores, citation drilldowns, agent tool-call timelines.

How a run works

  • A run is a materialization of a dataset against a pipeline — triggered from the operator console or CLI.
  • Content is chunked by markdown headers; each chunk gets LLM-generated search phrases (query-equivalent keywords, default gpt-4o, file-cached by chunk content+model+prompt+parser version).
  • Documents + chunks + phrases are upserted into three per-dataset Typesense collections.
Deterministic, versioned collections

Collection names are a SHA-256 hash of output-affecting config. Change the chunking strategy → new hash → new collections. The old ones stay intact until the operator flips the reference — atomic re-ingest, no downtime.

Pluggable + fault-tolerant
KudosEPiServerwebsite sitemapfolder

New source = implement the DocumentSource protocol + a loader adapter. Prepare/store run in parallel under budgeted failure (:fault-tolerance/max-document-failures).

Speaker notes The clever bit is versioned collections via config hashing — it turns "re-ingest with new chunking" into a zero-downtime pointer swap. Orchestration (pipeline.*) is deliberately separate from loading (docs.*); it's a mid-transition split, honest prototype tax.

PART II

Building it was half the work.
Making retrieval good was the other half.

Everything past here is eval-driven: measure, form a hypothesis, A/B a "lever," gate on a judge, keep or kill. Most levers died. A few didn't. The bugs we found in our own measurements were the best teachers.

Speaker notes Set expectations: this section is a research log, not a victory lap. The value is in the failures and the measurement bugs as much as the wins.

MethodHow we measured quality

Two harnesses, two questions
v3-scoreFast retrieval inner loop. Scores the retrieval skill vs golden chunks. Bypasses the agent. ~30s/run. "Did chunk/doc recall move?" sweep runnerFull agent loop. Cartesian config × question × repeat. Captures real cost + Filter-4 stage attribution. "Which stage lost the golden?"

The ground truth

  • Golden-chunk tuning loop — ground → query → goldens → score. ~59 questions.
  • LLM-as-judge — grades answers vs an authored reference (default judge model held constant).
  • Filter-4 decomposition — golden-in-pool? → in-display? → read? → answered?. Attribution, not a single number.
Speaker notes The rule of thumb: v3-score for "did retrieval move," sweep runner for "which stage is the bottleneck." Both kept, used for different questions. This distinction is what let us localize problems instead of guessing.

Challenge 1The bottleneck wasn't where any lever reached

Every upstream lever — corpus vocab, query expansion, phrase tuning, enrichment — failed. Because the loss was downstream, at rerank time.

  • ColBERT reranked the top-40, but scored each chunk truncated to 1000 chars — dropping the MIDDLE (head+tail kept).
  • Answer-bearing content lived in the dropped middle. Generic intros out-scored the real answer.
  • 74% of benchmark goldens were longer than the cap. Difficulty tracked golden length all along.
The fix — passage windowing (scoring-only)

Send ColBERT the best query-overlap window, not head+tail. The agent still reads the full chunk. Coarse chunks are good for reading, only bad for rerank scoring.

0.674→0.760

recall@20, full-42 · N=5 judged · every subset up, none regressed → promoted to default

Speaker notes The "swappable rerank" seam from pillar 3 is what made this a scoped fix. Lesson embedded here: check the golden's length before attributing a recall result to any retrieval lever. A whole run of prior arc conclusions was contaminated on the long-golden subset and had to be re-run.

Challenge 2 · the sharpest lessonA measurement bug faked a "model ceiling"

The bug

The sweep judge graded answers truncated to 800 chars — a :response cap in the runner that the separate judge pass read. The judge never saw the end of enumerative answers.

It manufactured a "54% under-enumeration ceiling" — which justified an entire model head-to-head arc chasing a bigger model to break a ceiling that was mostly an artifact.

After re-judging on full answers
partial-of-read54%→14%
effective quality.66→.75
Instrument the evaluator as carefully as the system. A/B deltas survived — the bug clipped both arms equally. That's exactly why it hid for months.
Speaker notes Key transferable insight: distrust absolute-difficulty narratives more than A/B deltas. A shared upstream bug preserves relative numbers while corrupting absolutes. Before concluding "we're at the model's ceiling," verify what the judge actually received. The fix added a judge-input assertion that warns on truncated input.

Challenge 3The premise itself was a single-run artifact

We opened a "retrieval coverage" arc believing ~20% of goldens never made the candidate pool. A clean re-baseline refuted the whole premise.

Pooled 503 runs, full-42
reachable42 / 42 questions never-in-poolzero golden-in-pool0.885 / run · min pool-rank 1–2

Where the "20%" came from

  • A single-run artifact — stochastic query variance read as structural failure.
  • A scaffolding bug — runs that never searched (passes=0) miscounted as "not covered."
Single-run failure cohorts are ~80% noise. Select cohorts by multi-run agreement, or you'll chase ghosts. No coverage headroom existed — the arc redirected upstream.
Speaker notes Same family of lesson as the evaluator bug: our diagnosis, not the system, was wrong. Two fixes came out of it anyway — a shape-agnostic "never searched → re-prompt" guard that took passes=0 from 0.27 → 0.00. But the headline is: verify the premise with replicates before building an arc on it.

The prompt in snippet-AB was load-bearing — rendering the snippet alone was +55% tokens for nothing. Mechanism matters more than surface.

Speaker notes Honesty slide. The ratio of dead levers to live ones is the real story of retrieval tuning. Snippet-AB was the first lever in the whole arc to reach statistical significance — and its win came from the prompt telling the model how to use the preview, not from showing the preview.

LessonMost levers are null — so gate hard

  • A/B at N≥5. The rerank fix whipsawed A→B→A purely on per-question N=3 variance. Replicates give a noise band; single runs give a story you'll regret.
  • Screens flip sign at scale. One interaction went +0.107 on an 8-question screen → −0.037 at full-42. An encouraging screen is not a result.
  • Ship A/B'd, not just "validated." A no-tool-call guard shipped "validated, not A/B'd" was inert in production — its regex missed real shapes. The skipped A/B would have caught it.

The screen filters cheaply; the full-42 judged run decides. Nothing is "promoted" without surviving the gate. Most things don't.

Speaker notes This is the meta-method. The screen-to-full pipeline plus N≥5 replicates is the machinery that turned a noisy problem into decisions we could trust.

LessonKnow a real ceiling from a fake one

After removing the fake ceiling (Challenge 2), a genuine one remained: under-enumeration in synthesis.

  • 87% of golden-read partials cited the golden — the content reached synthesis and was used — yet the answer still omitted required detail.
  • No plumbing trim to blame: full golden content reaches generate_response.
  • It's a 35B-local synthesis extraction limit — a bigger synthesis model would help; local prompt levers can't.
A directive made it worse

Telling the model to "enumerate everything, only from chunks" traded under-enumeration for over-reach — hallucination doubled, net-zero quality. Under-enumeration is not a prompt-instruction gap.

The whole game was telling a real ceiling from a measurement artifact. One justified a model swap. The other justified fixing our own ruler.
Speaker notes The satisfying symmetry: Challenge 2 was a fake ceiling that looked real; this is a real ceiling that we could only see clearly after fixing the measurement. The correct response to a real model ceiling is a bigger model or a scoped extraction step — not more prompt-poking.

Key takeawaysWhat we'd tell the next team

  • Config-as-data made it a platform. Skills-as-graph + config tree meant experiments were writes, not redeploys. That leverage paid for itself many times over.
  • Instrument the evaluator, not just the system. The judge's input is as load-bearing as its output.
  • The bottleneck is rarely where the lever is. Attribute the loss to a stage before tuning anything.
  • Distrust absolutes over deltas. Shared bugs preserve A/B deltas and corrupt absolute narratives — so "ceiling" and "no-lift" claims need the ruler checked first.
  • Gate everything at N≥5. Single runs and 8-Q screens are hypotheses, not results.
  • Know when you've hit the model, not the method. Stop poking prompts; change the model or the mechanism.
Speaker notes If they remember one thing: the measurement is part of the system. Most of our biggest "findings" were bugs in how we measured, and finding them was worth more than any single lever.
